## 1. Research question

Using only information that would have been available before each match, can
transparent football models produce well-calibrated probabilities that
contain useful predictive information beyond simple historical frequencies
and beyond the betting market itself?

Stage 3B is **probability-model validation**, not betting-strategy
optimisation. Staking, EV thresholds, odds bands, league filters, favourite
systems, accumulators, and bet counts are explicitly out of scope until a
later stage.

## 2. Dataset

Frozen Cycle 1 dataset, `data_version cycle_001_v1.0.0-20260910T234139` (see
`reports/audits/CYCLE_001_FREEZE_RECORD.json`). Every script in Stage 3B
verifies its local working copy against this frozen record's SHA-256 hashes
before reading any data (`scripts/verify_frozen_data_hashes.py`) and refuses
to proceed on a mismatch.

## 3. Development folds vs. final holdout

- **Sealed final holdout: 2024/25** (all 3 competitions). Not read by any
  Checkpoint 1-5 script. Opens only once, per a `FINAL_HOLDOUT_PROTOCOL.md`
  written and committed before it is touched (Checkpoint 5/6).
- **Development period: 2020/21, 2021/22, 2022/23, 2023/24.** Walk-forward,
  expanding-window folds (not one fixed train/validation split), generated by
  `validation.time_splits.generate_expanding_walk_forward_folds`:

  | Fold | Trains on | Evaluates on |
  |---|---|---|
  | `train_through_2020_21_eval_2021_22` | 2020/21 | 2021/22 |
  | `train_through_2021_22_eval_2022_23` | 2020/21, 2021/22 | 2022/23 |
  | `train_through_2022_23_eval_2023_24` | 2020/21, 2021/22, 2022/23 | 2023/24 |

  2020/21 is never itself an evaluation season (there is no prior season to
  train on) — it only ever contributes training rows. All development-fold
  results pool to 3,480 evaluation-match rows (2021/22 + 2022/23 + 2023/24,
  all 3 competitions).

  Folds are used for model specification, hyperparameter selection,
  calibration method, and blend weights. Folds are fixed now and are not to
  be redesigned after seeing results.

## 4. Baseline order

1. **Baseline 0 — naive historical frequency** (`models.football_naive_frequency`)
2. **Baseline 1 — market closing consensus** (existing `cycle_001_consensus_full.csv`, `price_timing == "closing"`)
3. Model 1 — Elo (not yet built)
4. Model 2 — Poisson (not yet built)
5. Model 3 — blends, only if individually justified (not yet built)

## 5. Baseline 0 definition

`models/football_naive_frequency.py`: for each match, an expanding,
per-competition H/D/A frequency computed only from strictly-earlier matches
in the same competition, with Laplace (add-1) smoothing so the first matches
of a competition's history get a well-defined 1/3-1/3-1/3-anchored
prediction rather than a 0/0 division. Deliberately simple — this is a sanity
floor, not a target to optimise. Leakage-safety is enforced by construction
(counts update only after a match's own prediction is recorded) and verified
by a dedicated regression test
(`test_football_naive_frequency.py::test_leakage_a_later_result_never_changes_an_earlier_prediction`).

## 6. Baseline 1 definition and price-timing classification

Every odds field used in Stage 3B is classified explicitly, per the
directive:

| Field | Source | Timing known? | Executable historical price? | May enter fundamental (market-free) models? | Role in Stage 3B |
|---|---|---|---|---|---|
| `cycle_001_consensus_full.csv`, `price_timing == "opening"` | football-data.co.uk archive, per-bookmaker opening odds, margin removed, median consensus | Yes (labelled opening) | No — no independent execution-timestamp evidence | No | Not used in Checkpoint 1; retained for future diagnostic use only |
| `cycle_001_consensus_full.csv`, `price_timing == "closing"` | Same archive, per-bookmaker closing odds, margin removed, median consensus | Yes (labelled closing) | No — same caveat | No | **`market_predictive_benchmark`** — Baseline 1 |

The closing consensus is used as `market_predictive_benchmark`: a valid,
strong benchmark for predictive comparison. It is explicitly **not** treated
as `historically_executable_entry_price` — there is no evidence in this
dataset of the exact timing, liquidity, or executability of any quoted price
relative to kickoff. Actual EV/trading-profitability analysis requires a
separate, legitimate entry-price framework, deferred to a later stage (see
directive §26).

**Consensus renormalisation note:** the median-per-outcome consensus does not
exactly sum to 1.0 (up to 1.18% deviation, median 0.13% — see
`reports/audits/CURRENT_STATE_AUDIT.md`, Update 4). Log loss and Brier score
require a genuine probability vector, so `scripts/run_stage_3b_checkpoint1_baselines.py`
renormalises (divides by the sum) rather than loosening the metric
functions' sum-to-1 tolerance to accept unnormalised input.

Consensus construction itself (per-bookmaker margin removal via
`probability.margin_removal.proportional_margin_removal`, then cross-bookmaker
median via `probability.consensus`) is unchanged from Stage 3A/existing
methodology — no change requiring re-versioning.

## 7. Common-sample comparison rule

Any paired comparison (naive vs. market; later, model vs. market) is computed
on the identical match-ID set for both sides. Coverage differs slightly
between naive (computable for every match) and market (requires
`eligible_consensus_model == True` and a closing-timing consensus row): 3,480
naive-full-coverage rows vs. 3,446 in the naive-vs-market common sample,
pooled across development folds. Both the full-coverage number and the
common-sample number are reported side by side — never mixed into one
"comparison."

## 8. Metrics and delta convention

Multiclass log loss and multiclass Brier score
(`performance.log_loss.multiclass_log_loss`, `performance.brier.multiclass_brier_score`),
both validated to reject malformed probability vectors (wrong keys, negative
values, sums outside ±0.1% of 1.0). Calibration/reliability reporting is
deferred to the model checkpoints (Elo/Poisson/blend), where there is
something non-trivial to calibrate beyond the already-well-calibrated
consensus.

Delta convention (fixed for the whole of Stage 3B):

    delta = model_metric - market_metric

Negative = model beats market. Positive = market beats model. Documented
once here, used everywhere.

## 9. Testing

Every module above has unit tests covering: probabilities always sum to 1;
no negative probabilities; deterministic output for identical input; a
dedicated leakage test (a later match's result must never change an earlier
match's naive-baseline prediction); the sealed holdout season is filtered out
by construction and never loaded; and an integration test that runs the real
verifier against the real committed freeze record. Full suite: 297/297
passing as of Checkpoint 1.
