## 1. Canonical observation schema

`src/prediction_markets_lab/research/market_observation.py` -- the
`MarketObservation` dataclass, tested (13 tests, `test_market_observation.py`).
One row = one player, in one real match, at one price-time horizon:
match/event/market/runner identity, player name and a/b role, final
scheduled start, observation cutoff and its horizon label, model
probability and fair odds, last-traded-price and its implied probability,
the normalised `market_reference_probability`, their delta, market
status/in-play flag, snapshot availability, price age (staleness), and
outcome. Missing data is represented as `None`, never fabricated.

## 2. Temporal-leakage safeguards

`build_pre_match_observation` mechanically asserts
`observation_timestamp < scheduled_start` for every record (an
`AssertionError` if that arithmetic were ever wrong) and rejects a
non-positive horizon outright (`ValueError`). `latest_price_at_or_before`
is the single function responsible for the price side of this guarantee
-- it filters to `timestamp <= cutoff` before ever selecting a point, so
a later, more-favourable-looking price can never leak backward into an
earlier observation. Tests cover: a post-cutoff price update is provably
never used even when it precedes the real match start
(`test_post_start_prices_never_leak_into_a_pre_match_observation`); a
missing snapshot returns `None` fields rather than a fabricated value;
`market_reference_probability` is `None` (not a guess) when only one
side has traded before the cutoff; staleness (`price_age_seconds`) is
computed correctly. `scheduled_start` is always the FINAL, post-revision
market time (`extract_market_facts` in the pipeline script takes the last
non-null `marketDefinition.market_time` across a market's whole message
history), directly applying the real reschedule discovery from the
sample audit. Wrong-runner-mapping is guarded in the pipeline script: a
match is skipped (not guessed) if both runner IDs can't be confidently
mapped to the TML player_a/player_b names via `names_are_equivalent`.
Duplicate messages/markets are handled by construction --
`latest_singles_event_candidates` keys by `market_id`, so re-parsing the
same message twice or seeing a market's history split across lines never
produces two competing candidates for one market.

| Horizon before scheduled start | Coverage (either side has a price) | Of available prices, % stale (>1h old) |
|---|---|---|
| 24h | 47.8% | 76.2% |
| 12h | 91.2% | 22.2% |
| 6h | 94.9% | 25.2% |
| 3h | 97.8% | 23.3% |
| 1h | 98.5% | 8.2% |
| 30min | 99.3% | 4.4% |
| 10min | 99.3% | 1.9% |

**24 hours before start has genuinely poor coverage** (under half of
matches have a price that far out) -- exactly the kind of horizon that
must not be frozen by assumption, per the operator's instruction. Coverage
is excellent (>97%) from 3 hours before start onward, and staleness drops
sharply as start approaches. **30 minutes before start was used as the
main descriptive-analysis horizon below** on data-availability grounds
alone (99.3% coverage, lowest staleness), not because it looked
interesting. This is a real, small-sample (N=136) finding, not a claim
about Betfair's general price-update frequency.

## 4. Market reference probability

Implemented as `market_reference_probability(price_a, price_b)`: the
normalised two-runner implied probability
`q_a = (1/price_a) / (1/price_a + 1/price_b)`, computed from each
runner's own last-known price at or before the same cutoff (their
timestamps can differ slightly -- both are simply the most recent point
each side had traded at by that cutoff). This is explicitly labelled and
treated as a **research reference probability**, never an executable
one: BASIC tier has no back/lay ladder, so whether Fraser could actually
have obtained that exact price is not established by this data. Raw
`1/last_traded_price` for a single side is kept as a separate field
(`raw_ltp_implied_probability`) and is never itself treated as "the"
market probability.

## 6. Elo-vs-market descriptive results (30-minute horizon, N=270 player-observations from 136 matches)

**Purely descriptive. No threshold. No promotion.** Mean model-market
delta is ~0 (as expected if both sides are individually reasonable),
stdev 0.100.

| model_probability minus market_reference_probability | n | actual win rate |
|---|---|---|
| [-1.00, -0.10) -- market much more confident than Elo | 39 | 64.1% |
| [-0.10, -0.03) | 55 | 49.1% |
| [-0.03, +0.03) -- broad agreement | 82 | 50.0% |
| [+0.03, +0.10) | 55 | 50.9% |
| [+0.10, +1.00) -- Elo much more confident than market | 39 | 35.9% |

A naive read of the two extreme bins (market noticeably more confident:
64.1% actual win rate; Elo noticeably more confident: 35.9%) would say
the MARKET was right more often than Elo when they disagreed sharply in
this sample -- i.e. no sign of an Elo-side edge, if anything the reverse.
**This is not reported as a finding.** N=39 per extreme bin is far too
small to distinguish a real pattern from noise (a 64%/36% split easily
arises by chance at this sample size), and per the operator's explicit
instruction, no relationship from N=136 is promoted either way. It is
recorded here only as: **CANDIDATE OBSERVATION -- REQUIRES FRESH
VALIDATION ON A LARGER, INDEPENDENT SAMPLE. Direction (if anything,
favouring the market over Elo at large disagreements) noted for future
reference, not acted on.**

Mean absolute disagreement is fairly flat across horizons (0.075-0.083
from 24h down to 10min) in this sample -- no clear convergence-toward-
start pattern was visible, but N is small and 24h's own coverage is only
47.8%, so this comparison itself is on a smaller, possibly unrepresentative
subset at the wide end. Not treated as a finding either way.

Naive calibration check at 30min (player-a rows, n=136): mean Elo
probability 0.492 vs actual outcome rate 0.544 -- consistent with the
mild overconfidence/miscalibration already on record for Global Elo from
Tennis Cycle 1 (A4/holdout calibration slope 0.81-0.87), not a new
finding.

## 9. Proposed chronological market-aware validation design (proposal only -- not executed)

The operator's concern: 2024 and 2025 outcomes were already used for
Global Elo's own predictive validation/holdout (Tennis Cycle 1). Reusing
them again for market-edge *discovery* is not the same kind of leakage
(Elo is frozen and unmodified; this is a different hypothesis -- pricing
error, not predictive accuracy), but reusing them for a market-edge
*holdout* would blur "genuinely untouched data" in a way worth avoiding
before any profitability claim is made.

**Proposal**: once 2021-2025 Betfair data is linked and observations are
built, use **2021-2025 entirely as the market-edge discovery/development
period** (exploring whether/how model-market disagreement relates to
outcomes, CLV-style reference-price movement, and calibration -- exactly
section 6's kind of analysis, at full scale and with proper pre-registration
of what's being tested before looking). Reserve **2026 onward as the
market-edge holdout** -- the only period that has never been used for
anything in this project (not predictive development, not predictive
validation, not the sealed predictive holdout, and not market-price
research). This mirrors the "wait for a genuinely new period" option
already on file in the project roadmap (§11) and gives the cleanest
available boundary given what's already been touched. **Not executed --
this is a design proposal for the operator/Fraser to confirm before any
2021-2025-scale profitability analysis begins.**
