# Backtest Data Feasibility Audit — Phase 1

**Date:** 2026-09-22
**Context:** "BACKTEST PHASE 1 — HISTORICAL REPLAY, FROZEN V1 VALIDATION & DATA FEASIBILITY" instruction. Step 1 of that instruction's 13-step execution order: "audit real repo data before building anything." This document reports only what was actually inspected in this repository on 2026-09-22 — no dataset described below is assumed or extrapolated from memory of an earlier session.

This audit supersedes nothing; it extends `research/cycles/CYCLE_003_FOOTBALL/PHASE3A_BACKTEST_FEASIBILITY_AUDIT.md` (2026-09-19), which reached the same core conclusion about price-timing (use the closing snapshot for both sides of the comparison) from a narrower, pre-money-qualification-gate perspective. That document is not superseded and is not re-derived here; this audit defers to its price-timing reasoning and adds what the money-qualification gate (added 2026-09-22) requires: a real kickoff timestamp, and a documented account of what "money-event-horizon" means in a historical replay.

## 1. Raw source data actually present

`data/raw/football/football_data_co_uk/{E0,E1,SC0}/{2020_21..2025_26}/*.csv` — 18 full-season files (6 seasons × 3 competitions) plus 6 small `*_excerpt.csv` files (validation fixtures, not used for backtesting). Row counts: E0 380/season, E1 552/season, SC0 228/season (SC0 has fewer teams). Every file was opened and its header read directly (not assumed from a prior session).

Columns confirmed present in every raw file: `Date`, `Time` (kickoff, e.g. `12:30`), `HomeTeam`, `AwayTeam`, full-time and half-time score/result, `Referee`, post-match match statistics (`HS/AS/HST/AST/HF/AF/HC/AC/HY/AY/HR/AR`), and a large per-bookmaker odds panel for 1X2, Over/Under 2.5, and Asian Handicap, each in opening and closing ("C"-suffixed) form. **Schema drift is real and already documented**: `data/processed/football/h_fb2_002_sealed_oos_2025_26_data_audit.json` recorded that the exact set of bookmaker columns changes across seasons (e.g. `WHH`/`1XBH` present in 2024/25, absent in 2025/26; `BFDH`/`BMGMH`/`BVH`/`CLH`/`LBH` appear only from 2025/26 on). Any code that reads raw bookmaker columns by a fixed hard-coded list will silently under- or over-count bookmakers across seasons — the existing `cycle_001`/`cycle_002` processing scripts already handle this by extracting per-bookmaker triplets dynamically rather than assuming a fixed column set, and the new backtest code reuses that same processed output rather than re-parsing raw columns by name.

The raw `Time` column is present in every file and every season but **has never before been threaded into any processed dataset** (see §3). Its timezone convention is not documented by football-data.co.uk and was not independently re-verified in this audit; it is treated here as the advertised UK kickoff time in local civil time (GMT/BST as applicable on that calendar date), which is the standard convention used by researchers working with this source. This is stated as an assumption, not a verified fact — see the Leakage Audit for how this assumption is bounded.

## 3. The kickoff-timestamp gap — found and closed for this audit only

**Finding**: no existing processed football dataset in this repository (Cycle 1 or Cycle 2) carries the fixture's kickoff time-of-day — only `match_date` (a date, no time). The raw `Time` column exists in every raw file (§1) but has never been extracted.

**What this audit did about it (read-only, not yet part of any committed pipeline change)**: a join was tested — for every `cycle_001_matches_full.csv` row, reformat `match_date` to `DD/MM/YYYY` and look up `(Date, HomeTeam, AwayTeam)` in the matching raw file (selected by `competition_code`/`season`). Tested exhaustively for E0/2020_21: **380/380 matches joined successfully** with an exact raw `Time` value recovered. This confirms kickoff time-of-day **is** recoverable from data already in this repository, but only via a fresh join the replay harness performs itself — it is not a field that already exists in any processed table. The replay harness (`src/prediction_markets_lab/backtesting/historical_loader.py`) performs this join for every match it processes and fails loudly (excludes the match, records the reason) rather than guessing a kickoff time for any match the join does not resolve.

The recovered `Date + Time` is interpreted as **Europe/London local civil time** (converted to UTC via the IANA tz database, which correctly handles the BST/GMT boundary for each specific date) — an assumption, not an independently verified fact about football-data.co.uk's own capture process (see §1). This is the single most load-bearing assumption in the entire backtest and is called out again, with its consequence, in `LEAKAGE_AUDIT.md`.

## 5. The money-event-horizon gate: an honest limitation, not a data gap

`decisions.money_qualification.assess_money_qualification` requires `kickoff_iso` to be strictly after `scan_timestamp_iso` and within `event_horizon_hours` (24h) of it. In live production, `scan_timestamp` is the real wall-clock time the daily scan ran (any time of day, hours or up to ~1 day before kickoff, driven by when the scheduled GitHub Action fires or a manual scan is run) and `kickoff_iso` is the fixture's real future kickoff time from The Odds API — the horizon check is a genuine, meaningful test of whether a fixture is "close enough" to bet on today.

In this proxy backtest, there is no independent historical "the scan ran at this real clock time" fact to recover — the only decision-relevant timestamp football-data.co.uk provides is the closing-odds snapshot, which by definition sits very close to kickoff (typically minutes to a few hours before). The replay harness therefore defines its simulated `scan_timestamp` as a small, fixed, explicitly-documented offset before the recovered kickoff time (`historical_loader.SIMULATED_SCAN_OFFSET_BEFORE_KICKOFF`, default 60 minutes) — **not** a real historical fact, but a modelling necessity, clearly labelled as such rather than presented as data. The direct, important consequence: under this design, `hours_to_kickoff` is always ≈1 hour, so **every single candidate trivially passes the 24-hour money-event-horizon check** by construction. This backtest therefore validates the probability/confidence/data-quality/odds/EV gates of money-qualification against real historical outcomes, but it does **not**, and cannot, meaningfully exercise the horizon gate itself — that would require genuine intraday multi-timestamp price history (an actual time series of odds through the day), which this repository does not have for any market. This is stated plainly in `performance.json`'s `proxy_disclosure` block for every run, not left implicit.

## 6. Data sufficiency verdict (Step 13 of the governing instruction, answered here for the 1X2 finding — the full 30-point checkpoint restates this)

**Sufficient for**: a real, honest, closing-snapshot-proxy frozen-V1 backtest of the 1X2 market across 3 competitions and 6 seasons (~5,800 matches, ~17,000+ candidate rows before any grading/qualification filtering), using the actual production probability/grading/payout/money-qualification code end to end, with a real (assumption-flagged) kickoff timestamp recovered from raw data for the money-horizon field even though that field cannot be meaningfully stress-tested by this data (§5).

**Not yet sufficient for**: (a) a meaningful Over/Under 2.5 or Asian Handicap money-qualification backtest — would need either more historical bookmakers per match for these markets (a different/paid data source, or a different free source with denser OU/AH panels) or an explicit, separately-approved decision to relax the money-qualification data-quality floor for a research-only OU2.5 run (out of scope for Phase 1 — no threshold changes permitted); (b) any exact (non-proxy) replay of the live 07:00 UTC daily-scan design or a genuine test of the 24-hour money-event horizon — this would need forward-collected, timestamped intraday price data (the kind this project's own live scans are now producing daily, starting 2026-09-20 per the automation commissioning), which does not yet span enough calendar time to backtest against; (c) any exchange (Betfair/Smarkets) execution-realistic backtest, per `docs/HISTORICAL_PRICE_AND_CLV_LIMITATIONS.md`'s existing, unchanged `true_execution_clv` restriction. Nothing here recommends purchasing a paid data provider — the existing free data is enough to produce one honest, clearly-labelled proxy result now, and the live daily scans already running are, over time, the actual fix for (b).
