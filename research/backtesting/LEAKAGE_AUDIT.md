# Backtest Leakage Audit — Phase 1

**Date:** 2026-09-22
**Scope:** every feature/input the frozen-V1 replay harness (`src/prediction_markets_lab/backtesting/`) feeds into the reused production decision pipeline (`probability.market_pipeline` → `decisions.recommendation.build_recommendation` → grading/payout/money-qualification), audited field by field against `docs/DATA_LEAKAGE_RULES.md`. Anything not provably leakage-safe below is excluded or explicitly flagged, per the governing instruction's zero-tolerance leakage requirement.

## Inputs used, and their leakage status

| Input | Source | At-or-before decision time T? | Verdict |
|---|---|---|---|
| Per-bookmaker 1X2 decimal odds (home/draw/away), closing snapshot | `cycle_001_bookmaker_markets_full.csv`, `price_timing == "closing"` | **This IS the defined decision time T** for this proxy (§5 of the feasibility audit: T is defined as the closing-odds snapshot itself, ~60 minutes before kickoff by construction). Not future information relative to T because T is defined to coincide with it. | SAFE, by definition of the proxy — not an exact replay of a genuinely earlier T, but not a leak either (see the explicit caveat this creates, discussed under "Residual risks" below). |
| Match result (`full_time_result`, H/D/A) | `cycle_001_matches_full.csv` | Used **only** for settlement, strictly after the recommendation (probability, grade, money-qualification, stake) has already been computed and recorded. The replay harness's own ordering enforces this: `replay.replay_match()` calls `build_recommendation()` and appends its result to the output list *before* it ever reads `full_time_result` for that match. | SAFE — verified by code structure and by `tests/unit/test_backtest_replay.py::test_result_is_not_read_before_recommendation_is_built` (asserts, via a poisoned/mocked result-reader, that no result is dereferenced until after the recommendation object exists). |
| Kickoff date/time (recovered via the raw-file join, §3 of the feasibility audit) | Raw football-data.co.uk `Date`/`Time` columns, joined by (competition, season, date, home team, away team) | The date and advertised kickoff time of the match itself — not derived from anything that happens during or after the match. | SAFE. |
| `accepted_bookmaker_count` / consensus dispersion (`std_dev`) feeding `decisions.confidence` and `decisions.data_quality` | Computed from the same closing-snapshot bookmaker panel as the odds themselves | Same snapshot as the price input — no additional information from a later point in time. | SAFE. |
| `quote_age_minutes` | **Not a real historical fact — a fixed constant (0.0) chosen by the replay harness**, documented in `historical_loader.py` | N/A — this is a declared modelling simplification, not fabricated data. Football-data.co.uk does not publish a numeric odds-age at the closing snapshot (it publishes a single closing price, not a timestamped tick). Setting it to 0.0 encodes "by construction, this snapshot is what 'current' means for this replay" rather than inventing an unknown real-world staleness figure. | SAFE from a leakage standpoint (it does not admit any future information) but flagged as a labelled simplification, not a measured fact — see the feasibility audit and `performance.json`'s `proxy_disclosure` block. |
| `no_material_info_risk`, `market_rules_match` | Fixed to `True` for every historical candidate (there is no way to retrospectively know whether team news existed at T, and no market-rules-mismatch is possible when both sides of the comparison are read from the same historical row) | N/A — these are the same two fields `decisions.grading.GradingInput` already documents as "a human-owned judgement for V1" even in live production; the replay cannot re-create a human judgement that was never made historically, so it defaults to the same neutral assumption live V1 uses when a human has not flagged a concern. | SAFE, but genuinely un-testable either way — recorded as a limitation, not silently assumed away. |
| `available_size_gbp` (exchange liquidity) | Not present in this data (bookmaker odds, not an exchange order book) — passed as `None` | Matches `decisions.liquidity.assess_liquidity`'s own documented behaviour for a bookmaker price (`available_size_gbp=None` → always adequate at V1's stake sizes), exactly mirroring how live V1 already treats bookmaker prices. | SAFE — no new assumption introduced beyond what production code already does for a bookmaker-sourced price. |
| Best-price selection (which bookmaker's closing odds is treated as "the price we'd have gotten") | The single highest closing decimal odds among the bookmakers that contributed a complete, accepted triplet to that match's consensus (i.e., drawn from `MarketConsensusResult`'s accepted set, never a rejected/incomplete bookmaker) | Same closing snapshot as the consensus itself — no cross-snapshot mixing (this is exactly the leakage risk `PHASE3A_BACKTEST_FEASIBILITY_AUDIT.md` flagged and the reason both sides of the comparison must come from one snapshot). | SAFE against timestamp-mixing leakage. Flagged separately as an optimism risk, not a leakage risk, below. |

## Explicitly excluded (not fed into the replay at all, and why)

- **Opening-snapshot odds, when the closing snapshot is used for the same match's decision.** Never mixed with closing data for the same candidate — each replay run uses one price_timing consistently for both the consensus and best-price side, per `docs.DATA_LEAKAGE_RULES.md` rule 1 and the pre-existing `PHASE3A` conclusion. Enforced in code by `historical_loader.load_matches_for_replay(price_timing=...)` accepting only a single timing value per run, never both.
- **Post-match statistics** (shots, corners, cards, referee) from `cycle_002_match_statistics.csv` — not used at all. Production V1's probability estimate is the raw bookmaker consensus, not a statistics-derived model, so these columns are irrelevant to this replay regardless of their leakage status; excluded per `docs/DATA_LEAKAGE_RULES.md` rule 5 as a matter of principle even though they are not consumed.
- **Elo/rolling-form features** (`cycle_002_discovery_features.csv`) and any Gate-1/H-FB2 model output — not used; V1 does not run a rolling-feature model in production (see feasibility audit §2.2), so there is no rolling-window leakage surface to audit here. If a future phase ever backtests one of the *researched* architectures (Elo/Poisson/blend) rather than the frozen V1 consensus-only strategy, that would require a full re-audit against `validation.leakage_checks.check_rolling_window_uses_only_past_data` — explicitly out of scope for Phase 1, which tests the frozen *production* strategy only.
- **Final-season standings / any full-season aggregate.** Not computed or used anywhere in the replay.
- **Any information about a match beyond its own closing-snapshot panel and its own kickoff date/time.** No cross-match information flows into a candidate's recommendation (each match's `build_recommendation` call is independent — no rolling state is threaded between matches), so `validation.leakage_checks.check_chronological_order` is satisfied trivially by construction rather than needing to be enforced by a stateful update order. It is still asserted directly in `tests/unit/test_backtest_replay.py::test_matches_processed_in_chronological_order` as a property of the harness's iteration order (ascending `match_date`), because the output bankroll/drawdown sequence *does* depend on processing order even though no per-match feature does.

## Residual risks (not leakage, but adjacent and disclosed)

1. **Optimism from "best of N bookmakers" price selection.** Taking the best closing price across every bookmaker that quoted a complete market is a reasonable, principled, and leakage-safe rule (same snapshot, real historical bookmaker prices, no future information) but it is more favourable than a real bettor checking a small number of bookmakers would typically achieve. This is an *optimism* risk to the reported ROI, not a leakage risk, and is stated as such in `performance.json`'s `proxy_disclosure` block and the final report, not corrected for in Phase 1 (correcting for it would be a threshold/methodology change, out of scope here).
2. **The Europe/London kickoff-time assumption (§3 of the feasibility audit).** If this assumption is wrong for some matches (e.g. a rare non-standard kickoff-time recording), the *only* thing it affects is the tautologically-passing money-horizon check (§5 of the feasibility audit) — it does not affect the odds, consensus, grading, or EV calculations at all, since none of those depend on kickoff time. Its blast radius is therefore already contained to a gate this backtest was never able to meaningfully test in the first place.
3. **`eligible_consensus_model == False` matches (24 of 5,800, per the feasibility audit) are excluded from the replay**, not force-included with degraded data — consistent with `docs/DATA_DICTIONARY.md`'s own "ineligible rows are flagged, never silently dropped from the master dataset" convention (the rows still exist in the underlying CSV and this run's `manifest.json` reports the exclusion count; they are just not fed into this particular replay).

## Verification mechanisms

- `tests/unit/test_backtest_replay.py::test_result_is_not_read_before_recommendation_is_built` — settlement ordering.
- `tests/unit/test_backtest_replay.py::test_matches_processed_in_chronological_order` — chronological processing, using `validation.leakage_checks.check_chronological_order` directly rather than re-implementing an ordering check.
- `tests/unit/test_backtest_historical_loader.py::test_price_timing_never_mixed` — a single run never combines opening and closing odds for the same match.
- `tests/unit/test_backtest_historical_loader.py::test_best_price_drawn_only_from_accepted_bookmakers` — the "best price" is never taken from a bookmaker `compute_market_consensus` itself rejected for an incomplete outcome set.
- `tests/unit/test_backtest_frozen_strategy.py::test_frozen_config_hash_is_deterministic` — the frozen-strategy hash (used to prove no threshold drifted mid-backtest) is reproducible from the same inputs.

No leakage was found in the design described above. The residual risks in the previous section are disclosed, not hidden, and none of them constitute a violation of `docs/DATA_LEAKAGE_RULES.md`.
